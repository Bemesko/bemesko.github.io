## The problem

The client's pricing team tests hypotheses against data that lives in Google BigQuery. Each cycle, from question to answer, took around two weeks. They wanted AI agents to shorten that loop.

The team building it was mostly low-code developers. So the challenge was as much about _how_ we built as _what_ we built: bringing software engineering practices to an AI project instead of treating it as one more low-code project.

## Starting from the product

Before writing any infrastructure I had to study product management and prototyping techniques, to reduce the risk of building something that wouldn't solve the client's pain. I ran the discovery and the sprints with the client directly.

One decision mattered more than any technical one: the client wanted a 98% accuracy target from day one. We agreed to postpone it until there was a real baseline, and to measure separately what drives that number: data quality, diagnostics, approved recommendations and financial outcome.

## The architecture

<LayeredDiagram id="fig-pricing" {...diagrams['pricing-agents']} />

- **Three agents on Azure AI Foundry**, each with a narrow job, orchestrated behind an app the pricing team uses in natural language.
- **An MCP server as the data gateway.** Agents never talk to BigQuery directly; one service centralizes every query.
- **Least privilege by default.** Segregated resources, and credentials that can read only the tables the agents actually need.
- **Cost guardrails from the start.** Budgets, tags and alerts were part of the first deploy, not a follow-up.

## Where it stands

The first production release shipped on day 66, with the app, the data gateway and the three agents in a single release. The client tested the first version in natural language a few days later. The project runs into early 2027.
